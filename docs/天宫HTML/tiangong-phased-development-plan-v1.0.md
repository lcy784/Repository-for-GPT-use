## 1. 计划边界与实施顺序

### 1.1 核心价值优先

先验证两件事：

1. **视觉价值：** 小人物站在巨殿前，建筑尺度、轮廓与光照值得继续投入。
2. **探索价值：** 操控同一人物从江南地面飞到天宫，切换视角、进室内、落屋顶。

因此在 P02 就制作重点视觉样本，在 P06 跑通核心体验，不等铺满地面或建完所有宫殿才验证。

### 1.2 与架构大阶段的对应

| 架构大阶段 | 本计划细阶段 | 阶段成果 |
| --- | --- | --- |
| 第一阶段：技术与视觉验证 | P00—P09 | 可重复测试的共用核心、重点视觉和探索路线、分区、简易离线 A 包 |
| 第二阶段：完整离线内容 | P10—P17 | 扩大地面、宫殿群、完整约定核心能力及 B 离线交付 |
| 第三阶段：允许的环境扩展 | X01—X04（选择后串行） | 经确认的昼夜天象、天气、简单 NPC、可能的音乐 |
| 第四阶段：少量联机 | N00—N04（正式启动后串行） | 3—5 人共同观景及服务器实测 |
| 按风险另立阶段 | Z 类变更阶段 | 确有必要的 WebGPU、Worker、浮动原点等；不得随手混入其他阶段 |

P00—P17 是建议的主执行链。每个阶段范围可独立验收，但不是互不依赖。**所有阶段仍严格串行，上一有效阶段 PASS 才能启动下一阶段。**

本计划不替用户回答 PRD 未定问题。涉及选型、A/B 范围、移动规则、视觉标准或水中能力的决策，必须在对应阶段开始前补齐。第一阶段样本范围不是取消完整产品要求。

## 2. 必须执行的累计回归制度

### 2.1 测试脚本规划

以下均为未来实施时必须创建的名称，本轮只在文档中定义：

- 总入口：`scripts/quality/gate.mjs`。
- 阶段入口：`scripts/quality/stages/P00.mjs` 至 `P17.mjs`。
- 可选扩展入口：`scripts/quality/stages/X01.mjs` 至 `X04.mjs`。
- 联机入口：`scripts/quality/stages/N00.mjs` 至 `N04.mjs`。
- 活跃阶段与用例清单：`quality/stage-manifest.json`。
- 验收环境与阈值：`quality/acceptance-profile.json`。
- 固定小场景／路径／输入：`quality/fixtures/`。
- 经审核图像基线：`quality/baselines/`。
- 本次门禁报告：`quality/reports/<run-id>/`。

建议技术：Node.js 门禁编排、TypeScript 类型检查、Vitest 状态与物理测试、Playwright 浏览器及产物测试。Playwright 可按配置分组运行浏览器测试 [T1]，并保存追踪及图像差异 [T2][T3]。具体兼容版本在 P00/P01 锁定，不使用运行时临时下载的测试依赖。

**每个阶段入口只运行该阶段自己的检查；总入口负责逐个执行全部阶段入口，避免递归累计造成重复膨胀。**

### 2.2 累计执行范围

记 G(Pk) 为 Pk 的独立阶段脚本：

- 完成 P00：必须运行 G(P00)。
- 完成 P01：必须重新运行 G(P00)、G(P01)。
- 完成 P06：必须重新运行 G(P00)、G(P01)、……、G(P06)。
- 完成 P17：必须重新运行 G(P00)、……、G(P17)。
- 开启扩展或联机后：必须重新运行全部主链、全部已通过且启用的扩展／联机阶段，再运行本阶段脚本。

计划中的统一调用形式为 `npm run gate -- --through P06` 等。**这些命令目前尚未实现，不能现在执行后声称测试通过。**

### 2.3 门禁算法与禁止事项

每次阶段检测必须：

1. 校验上一阶段 PASS 记录和当前允许执行阶段。
2. 校验所有应执行入口、必测用例编号和测试环境可用。
3. 为当前候选代码、依赖锁文件、配置和资产生成指纹，重新构建当前产物。
4. 在该候选版本上，逐个实际运行所有应执行的历史阶段脚本与当前脚本。
5. 每个入口输出用例数、通过／失败数、证据路径、退出码和环境身份。
6. 如出现失败，可继续跑其他诊断项收集证据，但总体始终 FAIL，不得放行。
7. 自动项通过后执行对应人工视觉或目标机检查；缺少必需证据为 BLOCKED。
8. 所有必需项通过才生成本次 PASS 和下一阶段进入资格。

强制禁止：

- 只跑改动相关测试、只跑最新阶段，或仅运行一次总构建。
- 用上一阶段昨天的报告代替本次重跑。
- 仅检查报告文件存在，不实际运行检测脚本。
- 将缺少脚本、空测试、超时、崩溃、必需环境不可用标为 PASS。
- 必测项使用 skip、todo、only、continue-on-error 或“无测试也成功”。
- 反复重试直到偶然成功，抹掉前次失败。抖动测试必须诊断并记录，不能靠绿色末次覆盖。
- 为通过测试自动更新截图基线、放宽阈值、删除历史断言。
- 将本轮文档检查当成游戏测试。
- 修改代码、资产或测试后继续复用修改前的门禁结果。

### 2.4 测试作用域

历史测试要在**当前实现**上重跑，而不是只在旧代码上重跑。

| 作用域 | 测试对象 | 防止的问题 |
| --- | --- | --- |
| 固定夹具 | 当前实现加载保留的小型测试地图和输入 | 地图扩大后失去原来的坡阶、薄墙、加载竞态复现条件 |
| 当前产品 | 当前世界内容、当前配置和当前构建 | 小夹具通过但完整地图已经损坏 |
| 分发产物 | 当前候选 A、B 生产包 | 源码开发页通过但发布包失败 |
| 目标 Windows | 当前候选在已记录设备与浏览器上运行 | 云端或软件渲染结果冒充本机画质、性能 |

从 P09 起，每次累计门禁都重建 A 并执行已承诺的 A 场景／移动／离线用例；从 P16 起同时重建 B 并执行 B 对应用例。并非把 B 独有内容强行要求 A 具有，而是**每个阶段脚本保留它已建立的适用矩阵并实跑**。不能在失败后临时把适用版本改为“不适用”。

### 2.5 可选阶段的顺序

- X 类不默认全部启动；音乐尤其仍为可选。
- 进入扩展／联机工作前，冻结本轮启用阶段的线性顺序。
- 未启用项登记 DEFERRED，不计为已完成或 PASS，不创建虚假的成功记录。
- 一旦某可选项被启用并进入执行链，必须完成并通过，才能进入其后阶段。
- N00 依赖 P17 和本轮所有排在它之前、已启用阶段的 PASS。
- 每次仍重跑所有实际已经完成的入口，不因“可选”省略回归。
- 若主动取消正在执行的阶段，需明确变更执行清单、移除或回退未验收功能，并重跑剩余全链；不能把失败改成 DEFERRED 继续带病开发。

### 2.6 状态与证据

状态：PLANNED → IN_PROGRESS → VERIFYING → PASS；失败为 FAIL，缺少规则／环境为 BLOCKED。DEFERRED 仅用于未启用内容。

每次报告必须记录：

- run-id、阶段编号、时间、代码标识／差异指纹、依赖与资产指纹。
- 本次候选 A/B 包哈希；尚未建立的版本标明未进入范围。
- OS、浏览器版本、图形后端、GPU 信息、分辨率、画质和测试模式。
- 每个阶段入口的开始结束时间、退出码、必测与实跑数量。
- 失败断言、预期／实际、截图／录像／trace、控制台与资源请求日志。
- 性能原始记录、人工视觉结论、遗留问题和回归缺陷。
- 下一阶段资格，不允许口头“基本完成”代替 PASS。

任何修改之后旧证据只作历史参考。已经开发到后期再改核心时，应重新计算从受影响阶段开始的验收有效性，并针对当前最高已完成阶段跑完整累计门禁。

## 3. 通用验收环境与失败处理

### 3.1 环境和阈值

P00 冻结基本测试环境、技术容差和视觉检查口径。后续需要的新参数必须在相应阶段开始前补充。

建议的工程测试规模：固定运动回放覆盖 30/60/144 帧显示节奏；资源压力至少 10 次跨区往返；关键转换至少重复 10 次；最终离线和服务器稳定性测试至少 30 分钟。上述数值是**本计划建议的测试强度，不是新增玩法需求**，审核后写入验收配置。

位置误差、支撑高度误差、图像差异容差、可接受卡顿和内存上限需在测试前明确；可以先测量并由评审冻结，不允许看到失败后临时提高。

性能目标仍为 60 FPS。分辨率、画质、平均／最低指标必须先确定；未确定时性能验收 BLOCKED，不能擅自改成 30 FPS。云端不具备真实目标 GPU 时，只能报告相应云端结果；目标机必需项须另行实际执行。

图像比较在相同环境与固定时间、随机种子、相机下进行。不同 GPU／OS 的结果分组管理，不能跨设备强行逐像素相等 [T3]。自动图像差异只检测退化，不能独自证明“已像参考图”，该项需要明确的人工作品评审。

### 3.2 任何阶段失败后的固定闭环 F

1. 停止进入下一阶段，保存本次全部失败证据和候选版本。
2. 分类为新增功能失败、前序回归、环境故障、素材问题或需求未定；不把环境故障算成功。
3. 用最小地图／输入复现；必要时在隔离副本上对比最后通过版本，不能拿旧版通过抵消新版失败。
4. 对可重复缺陷补充能先失败的回归用例，并归入责任阶段或明确关联套件。
5. 修复实现或资产；不通过删除断言、跳过用例、伪造基线修复。
6. 先跑缺陷用例，再跑责任阶段与当前阶段独立脚本。
7. 最后**从 P00 到当前阶段重跑全部应执行入口**；扩展与联机时包括此前全部已启用阶段。
8. 全通过后记录修复与新 PASS；否则保持 FAIL/BLOCKED。
9. 如需回退，保留可审查的修复／回退记录，不使用破坏性重置清除无关工作。回退后仍须全链复测。

后文各阶段的“失败处理”均必须与本节 F 一起执行，而不是只跑列出的局部检查。

## 4. 第一大阶段：离线技术与核心价值验证（P00—P09）

### P00 · 范围决策、验收契约与累计门禁

**目标：** 后续开发有明确边界，而且测试系统确实能拦截历史回归。

- **开发架构部分：** M15；M01—M14 的输入输出契约；架构第 2、4、9、15 节。
- **进入依赖：** PRD 和架构可读取；用户认可将本架构作为实施基线。没有前置开发阶段。
- **具体技术：** Node.js 阶段清单校验与门禁编排；用版本化 JSON／Markdown 记录决策；Vitest 测试门禁本身。
- **独立边界：** 本阶段只交付下面列出的能力；其他模块只做必要适配，不夹带下一阶段功能。

**开发任务：**

1. 逐项记录架构 A-01—A-06 的采用／修改状态；确定 A 简易版的初始功能范围、B 启动候选方式。重大决策未定时保持 BLOCKED。
2. 为 P02/P06 定义首个巨殿样本、参考图、审核机位和必保留要素；确定早期测试的显示条件及临时运动参数，不据此定死全世界地图尺寸。
3. 建立 PlayerIntent、PlayerState、WorldManifest 的逻辑契约、单位／坐标约定和唯一状态写入规则。
4. 建立阶段登记、用例编号、必测数、状态与报告契约；明确自动与人工项谁提供证据。
5. 实现总门禁及 P00 检查入口；此时只要求 P00 的真实检查可执行，未来阶段先登记名称，不能创建空成功脚本。
6. 用隔离测试夹具模拟上一阶段失败、脚本缺失、子进程非零退出、空用例和证据哈希不匹配；验证全部会阻断。

**完成后的成功体现：**

- 存在可审阅的阶段清单和最小实施决策，没有将未定玩法写成已确认。
- 门禁能运行 P00 真实检查并产出报告；故意注入失败必定返回失败。
- 下一阶段只能在 P00 所有必需项通过后进入。

**本阶段新增检测：**

| 用例编号 | 检测项 | 可验证断言与证据 |
| --- | --- | --- |
| P00-01 | 文档与契约检查 | 来源文档存在，首轮范围和需先决策的字段有明确记录，测试阈值不是占位字符串。 |
| P00-02 | 假阶段故障注入 | 单测模拟缺失入口、非零退出、0 测试、skip 必测项，门禁全部拒绝。 |
| P00-03 | 累计执行检查 | 用假的阶段执行器验证 P00→P01→P02 逐个被实际调用且不重用旧结果；测试对象是门禁，不是未开发游戏。 |
| P00-04 | 证据绑定检查 | 更改候选指纹、资产或用例清单后旧 PASS 不能放行；日志可以追溯失败入口。 |

**累计回归与放行：**

- 阶段入口：`scripts/quality/stages/P00.mjs`；统一调用：`npm run gate -- --through P00`（未来实现）。
- 无历史阶段；运行 P00 自检与故障注入。

## 7. 累计门禁的具体执行示例

### 7.1 完成 P06 后

本次必须逐个实际执行：

P00 → P01 → P02 → P03 → P04 → P05 → P06。

即使 P06 只改宫殿入口，也要重跑启动、视觉、行走、飞行、人物、双视角等原有脚本。新入口能进而 P04 飞行退化，本阶段仍 FAIL。

### 7.2 完成 P13 后

本次必须逐个实际执行：

P00 → P01 → P02 → P03 → P04 → P05 → P06 → P07 → P08 → P09 → P10 → P11 → P12 → P13。

- 重新构建当前 A 包。
- 重跑 P09 的 A 离线、路径和核心用例。
- 在当前实现上重跑固定旧夹具，以及当前完整地面、天宫、水域。
- 关门测试通过但旧屋顶穿模、A 黑屏、地面路线时间被改变，均不放行。

### 7.3 开启部分扩展后完成 N02

假设用户本轮启用了 X01、X03，X02、X04 未启用；冻结顺序为 P17 → X01 → X03 → N00 → N01 → N02。

则本次必须执行：

P00—P17 全部入口 → X01 → X03 → N00 → N01 → N02。

未启用的 X02、X04 继续显示 DEFERRED，不计入完成数；已经完成的 X01、X03 必须重新执行，不能认为“跟联机没关系”而略过。

### 7.4 修复后怎么判定

例如 P13 发现 P04-02 薄墙检测失败：

1. 保存 P13 失败报告和薄墙穿透轨迹。
2. 在 P04 的固定夹具重现问题；确认是否由门碰撞更新、角色控制或公共查询引起。
3. 增加能失败的回归断言，修复对应模块。
4. 局部验证缺陷用例、P04、P13。
5. 最后重新执行 **P00—P13 全部脚本**，并重建、检测 A。
6. 新的完整报告通过才批准进入 P14；局部全绿不是放行依据。

若问题是目标设备暂不可用，保持 BLOCKED；不得写“云端通过，默认本机也通过”。

- 真实路线时长用实际经过时间检查；加速模拟只可验证逻辑，不能替代 6—8 分钟实走或 30 分钟稳定性证据。

## 12. 工作量、变更与实施约束

- 本文没有承诺开发日期。阶段大小以能独立验收为原则，不把多项高风险功能合成一次交付。
- 每阶段可在内部拆任务或修复批次，但不允许绕过累计门禁直接进入下一阶段。
- 发现阶段过大可以在执行前拆分为例如 P11a/P11b，必须更新线性顺序、用例登记与累计范围，不能事后拆分来豁免已经失败的测试。
- 用户要求全历史实跑，因此验收耗时会随阶段增加。可以改善测试稳定性、夹具和同次构建复用，但不能把全量回归替换为仅受影响测试。
- 必需手工视觉和目标机测量由实际执行者提供同一候选证据，门禁验证证据身份后才放行；资料缺失不是测试通过。
- 允许使用库、引擎和开源素材，不保证找到全部匹配参考图的现成模型；素材失败应反馈具体缺口，不能靠临时网上热链接完成。
- 依赖版本升级、渲染后端切换、坐标规范变化或基础物理替换，均须单独变更评估，并重跑最高已完成阶段的累计门禁。
- WebGPU、Worker、浮动原点、精细体积云、桌面壳目前都不设为默认实现项；确需引入时单列目标、依赖、用例和失败处理。
- 本计划的测试数量是规划，不是已经存在的脚本数量；本轮不会创建空脚本来满足数字。
